## 読み方

画面番号は、この資料で場所を指し示すための番号です。ゲーム画面への番号表示や配置変更は行っていません。

`src/main.ts` に登録されている25個のSceneを01〜25、複数画面で使う共通パネルを26としました。同じScene内の表示切り替えには枝番を付けています。

今回はコードの座標、サイズ、表示条件、描画順、文字の折り返し設定を確認しました。ブラウザ自動操作・スクリーンショット・テストは実施していません。文字の実際の幅、高さ、端末のキーボード表示は未実測です。

- **A: 優先確認** — 現在の実装で、指定の条件になると領域が衝突する設定がある。
- **B: 拡張・内容に注意** — 長文、項目追加、編集内容などによって崩れやすい。現状で必ず崩れているという意味ではない。
- **C: 大きな衝突は未検出** — 読んだ配置では大きな衝突を見つけていない。実機での保証ではない。

## 全画面共通の基準

ゲーム内座標は **横390 × 縦844**。以下の割合は、端末の画面全体ではなく、このゲーム領域に対する割合です。

`index.html` の表示幅は `min(100vw, 100svh × 390 / 844, 430px)`、`src/main.ts` は `Phaser.Scale.FIT` です。ゲーム全体を同じ比率で縮小する構成なので、広いPC画面でも内部の配置間隔は増えません。端末幅に対する比率と、ゲーム内の幅に対する比率を分けて考える必要があります。

よく使うカード幅334は **85.6%**、左右余白28は各 **7.2%**。ただし縦方向は画面ごとに固定座標を置いており、共通の「本文の下端」「操作の上端」はありません。

今回の衝突は、領域の割り当てや内容の増え方を各画面で個別に決めていることから説明できます。エンジンの変更を前提にせず、まず表示領域と、入り切らない場合の扱いを決めるのが適切です。

## 優先して確認したい箇所

### 14-1 ショップ: 購入結果がカードの後ろになる

- `src/game/scenes/previews/ShopPreviewScene.ts:111` の描画順は、ヘッダー → タブと結果文 → 商品カード。
- 結果文の中心は166。4商品以上の場合、最初のカードは214−58=156から272。結果文がその内部にある。
- カードの塗りは不透明度0.96で、結果文より後に描かれる。完全透明ではないため、背面の文が大きく覆われる。
- **確認操作:** アイテムを1つ購入して直後の案内を見る。
- **見直す方向:** タブ、結果案内、商品一覧にそれぞれ高さを割り当てる。文字だけを前面にしても、商品欄との領域競合は残る。
- 5商品目のカードは628〜744となり、下部案内の中心724に重なる。商品追加前にページ送りが必要。

### 12-1 バトル: 複数行問題で入力と判定が重なる

- `src/game/scenes/battle/BattleGameScene.ts:1043` 付近で、明示的な改行数によって問題と入力のy座標だけを変える。
- 入力表示は2〜3行問題で566、4行以上で584。判定表示は574固定。中心間隔は8または10しかない。
- `submitAnswer` / `submitTwoPartAnswer` は誤答後820ms、入力表示を消さずに正答を表示する。
- **確認操作:** 複数行になる問題で誤答する。対象問題を出す対戦相手・ボスの設定で確認する。
- **見直す方向:** 問題、入力、判定の領域を分ける。明示的な改行数だけでなく、自動折り返し後の高さも考慮する。

### 24 方眼エディタ: 方眼とモード選択が衝突

- **確認操作:** 「たて＋」で8×8にして最下段と「キャラ／しかく／ぬる／わくけす」を見る。
- **見直す方向:** 方眼用領域を操作欄の上端より上で終わらせる。方眼の背景とラベルの余白も含めて確保する。

## 長文・項目追加に共通する注意点

### 「折り返しあり」だけでは縦のはみ出しを防げない

02、09、13、15、19、20、22、23、26は、横幅を指定したテキストと固定位置の後続要素を組み合わせています。横幅を守るために増えた行が、次の要素に入ることがあります。

特に21の制作入力はHTML textareaでスクロールできますが、22の再生本文は同じ仕組みではありません。「編集時に入力できた」ことと「再生時に会話枠に収まる」ことは別です。22の本文領域はy=694〜814の120（画面高さの14.2%）を目安に、ルビ・文字サイズ指定も含めて考える必要があります。

共通ボタン `src/game/ui/common/button.ts` は文字の幅・高さに応じて縮小しています。一般の `.text()` やRichTextには同じ処理が一律にかかりません。また、ボタンに収まっても文字が小さくなりすぎる問題は残ります。

### ページ送りの有無が場所によって違う

- 対応済み: お知らせ、ジャンル、ステージ、対戦相手、仲間、図鑑、背景商品、かけら交換、トロフィー、お話一覧、BGM一覧。
- 追加時の設計が必要: 通常の商品、属性別アメ交換、ミッション、旧会話ログ、進化列。
- ミッションは現在3件。仮に4件を未受取のまま全達成すると、全達成パネルは中心818・下端872となる。
- アメ交換は3列で中心y=626から62ずつ下がる。12属性なら最後のボタン下端838、13属性なら900。この数字は拡張時の境界であり、現行の有効属性数を示すものではない。
- 進化画面の列は4段階で丸の端がパネル外、5段階では画面外に達する計算。現行データで5段階あると断定したものではない。

### 編集できる画像は、中心ではなく外周を考える

01/17は `TitleEditScene.ts:703` の制限が中心座標に対するものです。x=44で幅170なら、回転前の画像矩形は左へ41はみ出す計算になります。実際の見える部分は素材の縦横比・透明部分によって変わります。

既存の自由な飾り方を仕様として残す場合は、強制的な制限よりも表示範囲のガイドが適しています。画像を必ず収める場合は、回転と拡大後の外周を使う方針が必要です。

### スマートフォンのHTML入力は別途手動確認する

18のコード入力、21の本文・名前入力、24の入力欄はHTML要素を使っています。21/24はCanvasの表示位置から入力欄を配置していますが、キーボード表示中の見える範囲は静的座標だけでは確定できません。

特に18はパネル全体の高さ上限・スクロールがないため、縦の狭い端末、横向き、キーボード表示中を確認対象にします。現時点で特定機種での不具合を実測したものではありません。

## 次に表示領域を決めるなら

まず **問題画面、カード一覧画面、詳細画面、制作画面** を分けて考えるのが適切です。全画面に同じ縦比率を当てる必要はありません。

それぞれで「ヘッダー」「本文」「操作」「通知」の範囲を決め、各範囲について次を明文化すると、機能追加の影響が読みやすくなります。

1. 開始位置と最大幅・最大高さ。
2. 文字が入り切らない場合に、縮小・省略・スクロール・ページ分割のどれを使うか。
3. 項目数が上限を超えた場合のページ送り。
4. 条件付きボタンを表示しない場合に、その空間を残すか詰めるか。
5. 見た目の矩形だけでなく、タップ判定・枠線・ルビ・演出の余白を含めるか。

この資料は現状と候補の整理です。ゲーム仕様、保存形式、表示位置は変更していません。
